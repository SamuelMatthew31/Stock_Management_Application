# Stock Manager

A Spring Boot REST API for managing products and suppliers. Product records are stored with Spring Data JPA and can be associated with a supplier. The project uses PostgreSQL as its database and Maven for building and testing.

## Features

- Create, list, retrieve, update, and delete products
- Create suppliers
- Associate a product with an existing supplier
- Validate product names, stock quantities, and prices
- Return structured responses for not-found and product-validation errors
- **Separation of Concerns:** Implementation of Data Transfer Objects (DTO) and Mapper pattern to decouple entities from the API layer
- **Pagination and Filtering:** GET products endpoint supports pagination and name-based filtering
- **Unit Testing:** Service layer testing integrated using Mockito and Spring Boot Starter Test (mocking repositories without hitting an actual database)

## Run Locally

On Windows PowerShell or Command Prompt:

```powershell
.\mvnw.cmd spring-boot:run
```

On macOS or Linux:

```shell
./mvnw spring-boot:run
```

The API is available at `http://localhost:8080`. The application is configured to connect to a PostgreSQL database named `stockmanager` running locally on port `5432`. Ensure your PostgreSQL server is active, and configure the necessary `DB_PASSWORD` environment variable before starting the application, as expected by `application.properties`.

## API

All request and response bodies use JSON.

### Products

| Method | Endpoint | Description | Success status |
| --- | --- | --- | --- |
| `GET` | `/api/products` | List all products | `200 OK` |
| `GET` | `/api/products/{id}` | Get a product by ID | `200 OK` |
| `POST` | `/api/products` | Create a product | `201 Created` |
| `PUT` | `/api/products/{id}` | Update a product | `200 OK` |
| `DELETE` | `/api/products/{id}` | Delete a product | `204 No Content` |

Product fields (adapted to DTO structure):

| Field | Type | Rules |
| --- | --- | --- |
| `id` | number | Generated by the server in responses; omit when creating or updating |
| `name` | string | Required and must not be blank |
| `stock` | integer | Must be zero or greater |
| `price` | number | Must be zero or greater |
| `supplierId` | number | Required integer referencing an existing supplier's `id` during resource creation and updates |
| `supplierName`| string | Returned in read responses providing the associated supplier's name directly |

Create a supplier first, then use its returned ID when creating a product:

```http
POST /api/suppliers
Content-Type: application/json

{
	"name": "Northwind Supply",
	"city": "Seattle"
}
```

```http
POST /api/products
Content-Type: application/json

{
	"name": "Desk lamp",
	"stock": 24,
	"price": 39.95,
	"supplierId": 1
}
```

`PUT /api/products/{id}` accepts the product fields and updates `name`, `stock`, `price`, along with the `supplierId`. The supplier association can now be changed through updates via the newly implemented DTO.

### Suppliers

| Method | Endpoint | Description | Success status |
| --- | --- | --- | --- |
| `POST` | `/api/suppliers` | Create a supplier | `201 Created` |

Supplier fields are `name` and `city`; `id` is generated by the server. Although these fields have non-blank constraints on the entity, the current supplier endpoint does not trigger bean validation.

### Error Responses

Product and supplier lookup failures return `404 Not Found`:

```json
{
	"status": 404,
	"message": "..."
}
```

Invalid product create or update requests return `400 Bad Request` with field-level validation details:

```json
{
	"status": 400,
	"message": "Validasi gagal",
	"errors": [
		{
			"field": "name",
			"message": "Nama tidak boleh kosong"
		}
	]
}
```

Validation messages are currently written in Indonesian. A product referencing a supplier ID that does not exist also returns `404 Not Found`.

## Architecture Improvements: DTO and Mapper

The application architecture has recently been enhanced with the introduction of **Data Transfer Objects (DTO)** and a **Mapper Layer**:

- **DTO (Data Transfer Object)**: `ProductRequest` and `ProductResponse` classes were introduced in the new `dto/` package. This creates a clear boundary between the API layer and the internal database layer (JPA entities). It prevents domain model leakage, avoids over-posting vulnerabilities, and helps structure the API payloads cleanly.
- **Mapper Pattern**: A `ProductMapper` class was implemented in the `mapper/` package. This component safely handles the transformation of internal `Product` entities into `ProductResponse` DTOs and `ProductRequest` DTOs back into entities mappings. This keeps the controller and service classes clean, highly cohesive, and tightly focused on HTTP routing and business logic respectively.

## Project Structure

```text
src/
	main/
		java/com/example/stockManager/
			controller/    REST endpoints
			dto/           Data Transfer Objects (e.g., ProductRequest, ProductResponse)
			exception/     Not-found exceptions and global error handling
			mapper/        Mapping logic between Entities and DTOs (e.g., ProductMapper)
			model/         Product and Supplier JPA entities
			repository/    Spring Data JPA repositories
			service/       Application and persistence operations
		resources/
			application.properties
	test/java/com/example/stockManager/
		StockManagerApplicationTests.java
```

## Current Scope

The API currently supports full CRUD with pagination and filtering for products, but only creation for suppliers. There is no authentication or authorization implemented yet.
